# Durable execution and session protocol — beta freeze

Artifact: `@nylorun/harness@0.14.0-beta.3`. Package version is separate from protocol 1, definition schema 5, durable checkpoint 1 / engine `hosted-4`, and inner execution checkpoint 1. Public execution API and shared contracts are the compatibility boundary. Cloud installs published npm packages and does not import the OSS Runtime.

## HTTP (both hosts)

Bearer application credentials: `PUT /v1/agents/:agentId` (`PutAgentRequest`: requestId, complete manifest, implementationVersion); `PUT /v1/sessions/:sessionId` (`PutSessionRequest`: requestId, agentId, trusted ownerUserId, optional info, optional `environment` — the id of an Environment (protocol 11): its sandbox (kinds `virtual` and `pod`) and its vault are the session's, with the recipe it applies pinned at open; omitted means no sandbox and no credentials; fixed for the session's life); `GET /v1/sessions/:sessionId`; `POST /v1/sessions/:sessionId/commands`; `GET /v1/sessions/:sessionId/items?cursor=...`; `GET /v1/sessions/:sessionId/events?cursor=...` (SSE, Last-Event-ID also accepted). Environments (`PUT/GET/DELETE /v1/environments/:environmentId`, `/stop`, `/reset`, `/events`, disk versions) and their secrets (`PUT/GET/DELETE /v1/environments/:environmentId/secrets/:name` and `GET .../secrets`: names, types and bindings, never a value) are Runtime API routes. Bearer management keys (the Management API, protocol 8; an application key there is `403 key_role_mismatch`): the `/v1/tenant/*` model routes below, the tool policy (`/v1/tenant/tool-policy`) and the Tenant's settings. Commands use `SessionCommandSchema`. A `message` command is exactly one of `{ content: string }` or `{ data: JsonValue }`, plus optional `manifest` (turn-only agent variant; see Turn manifests below). Application principals may call `POST /v1/sessions/:id/sandbox/:tool` for session-scoped sandbox built-ins when the session has a sandbox and no active agent turn. An Environment whose owner guard (`ownerUserId`) names another owner cannot be named by the session (the opaque `404`). `GET /v1/tenant/model` returns `{configured:false}` or the active provider, model, authType, and optional baseUrl, never the secret. `PUT /v1/tenant/model` upserts a host-scope provider credential and makes it active (idempotencyKey, requestId excluded from comparison). `PUT /v1/tenant/model/selection` switches the active provider/model among configured credentials without a new secret. `GET /v1/tenant/providers` lists configured providers with name, model, authType, lastUpdated, and active. `GET /v1/tenant/models` returns the public provider catalog, each model with the inputs it reads (`inputs`) and those the operator may add (`addableInputs`); `PUT /v1/tenant/models/inputs` sets the added ones (protocol 12), and `GET /v1/tenant/providers` gives each provider's `inputs`. agentId, ownerUserId, info and environment stay the creation identity. GET session returns id, agentId, ownerUserId, status, activeTurnId, `environment: { id, version } | null`, the pinned `harness`, `closedReason` on a closed session, mcpSnapshot, mcpDiagnostics, plus inspectable waits/uncertainty as available. mcpSnapshot is null until the first turn discovers MCP tools; it is then pinned for the session (v2, protocol 15: what the servers listed, by their own tool names, disabled tools included) and contains no secrets. History returns `{items: LiveEvent[], cursor: string|null}`; empty history cursor is null.

**Manifest-only agents (protocol 8, track R2).** The Runtime runs the whole agent from its manifest and its definition files, and never calls the developer's code during a session: Action endpoints, delivery tokens, background tools and held runs are gone (`/v1/endpoints` and `/v1/actions/*` answer `404`). An agent's tools are HTTP tools (`http`), remote MCP servers, agents used as tools and the Runtime's built-ins. `PUT /v1/agents/:agentId` refuses (`400`) a definition with a tool that has no `http` and no `agent`, and a flow agent with a `tool` stage (`codeToolRefusal` in `/define`); a tool effect the Runtime cannot run fails with `tool.unavailable`. `tool({ run })` runs only in the local engine (`/run`).

**Tenant and protocol headers.** A Host serves the one Tenant of its
installation, and nothing in a request selects it (protocol 5). Every Tenant
route requires `Nylorun-Protocol` (client protocol integer). Missing or
unsupported protocol → `426` with
`{ status: "rejected", code: "protocol_unsupported", protocol }` before
authentication, except that a request with neither `Nylorun-Protocol` nor
`Authorization` gets the route's `401` challenge (protocol 9). The Host serves
protocol 15 only (protocol 15 moved `read_artifact` and `save_artifact` to the harness, a fresh start for
agent sessions, and the choice of how each file reaches the model: a message may name any file,
`turn.start.model` describes the model, and the Model Gate only fetches and translates; protocol
13 changed the agent manifest to v7, the flat manifest, so an older client is answered `426`;
protocol 12 added model inputs). A `Nylorun-Tenant` header naming the Host's Tenant is
accepted, one naming another Tenant (or a malformed one) is the opaque `404`. A Tenant id in the query string or body is ignored. A
Tenant that could not be opened and an unknown Tenant share the opaque `404`
body. A missing or rejected credential is `401` (`credential_required`,
`credential_invalid`) with `WWW-Authenticate: Bearer` (protocol 9); on the
Runtime API the challenge names `/.well-known/oauth-protected-resource` when
the Host has trusted issuers. The Admin API is gone (protocol 8): `/v1/admin/*`
is no route, and the admin key is no request's credential. Vocabulary:
[runtime/server/src/CONTEXT.md](../server/src/CONTEXT.md).

Unauthenticated `GET /health` returns status, `service: "nylorun-runtime"`,
version, `hostId`, pid, and `protocol: { min, max, features }` (plus diagnostic
`coreVersion`). Clients treat unknown fields as optional so an older parser
still works. `GET /ready` is `200` only after the listener is up and the Host's
Tenant is open; a Tenant that cannot be opened fails it with its cause
(`schema-too-new`, `kek-missing`, `database-layout-old`, …), also reported in
`nylorun-operate status` inside the runtime container (`nylorun status` on a local Tenant).

All command idempotency keys bind to canonical request content within a session; requestId is transport metadata and is excluded from content comparison; exact semantic duplicates return the stored original response; changed content conflicts (409). Tool calls are delivered at least once (R5): an MCP or HTTP call a crash, a shutdown or a lost gate hop interrupted is sent again with the same key, its effect id (`Idempotency-Key`, or `_meta["nylorun/idempotency-key"]` for MCP), up to 3 sends; then, and for a sandbox or harness call at once, it fails to the model as `tool.interrupted` and is not run again. No tool call leaves its session `uncertain`. Results after cancellation cannot resume a turn. No hardcoded production credentials.

## Engine host

`createDurableCheckpoint({manifest,sessionId,turnId,input,state?,info?,segment?})`, `runDurable({manifest,checkpoint,host,signal?,mcp?,engineTools?})` from `/run` (`engineTools(agent)`: what our engine adds to each agent of the tree, `{tools, instructions}` from `engineToolsFor(agent, turn.start.environment, options)`: the sandbox, skill and artifact tools and their text, offered after the agent's own tools and before the MCP tools, not hashed; `mcp`: the session's MCP tools as our engine offers them, `mcpToolSet(turn.start.mcp, manifest, {config, model?, layout?, taken?})`, in place of `sessionTools` (protocol 15): named for the model, deferred tools behind `tool_search` and `tool_call`, each call targeting the tool's identity, with the layout the segment's state keeps as `mcpLayout`, not hashed). `DurableHost.resolveEffect(HostEffect)` atomically creates or reads an individually identified effect and returns `{status:'completed',outcome:{value,statePatch?}}` or `{status:'pending'|'uncertain'}`. Model effect `input` is the complete ModelCall (instructions/history/tools/output schema); context contains invocationId and, for a call that summarizes history, `compaction: {trigger, tokensBefore, keptTokens}` (its invocationId starts with `compaction-`). When history no longer fits the model's window, the engine replaces the older transcript entries with one `compaction` entry and keeps the rest; hosts publish `context.compacted` for such a call instead of `message.assistant`. Its completed value is a ModelCandidate, a string, or a failure outcome `{kind:'failed', code, message, retryable, retryAfterMs?}` for a provider failure the Runtime classified (codes in `MODEL_FAILURE_CODES`); the engine fails the step with `model.<code>`. A classified failure is a known outcome, not a lost one, so it is never `uncertain`. Runtime provider code owns credentials and invocation. Tool effects have toolName (the name the model called, for display), `target` (what runs the call, by identity, protocol 15: `{kind: "mcp", server, tool}` with the server's own tool name, `{kind: "http", tool}` with the declared name, `{kind: "sandbox"}` or `{kind: "harness"}`; the host routes by it, never by name, and it is in the request hash; an author's code tool has none, and the host fails it), optional `skill`, serialized input and context. The agent's `tools`, our engine's and the MCP tools never share a name: a clash fails the turn (`agent.build-failed`); an MCP tool whose name is taken is left out. Tool result value is a ToolOutcome or a plain tool output, shaped by the API host before it is recorded (`shapeToolOutcome`, `StepBudget`: one record entry at most, the rest stored as artifacts keyed by `spillKey`); statePatch contains changed session keys. Tool context includes invocationId, resume, state, info and stable idempotencyKey. Customer implementationVersion is pinned by the runtime outside durable checkpoints.

Persist checkpoint BEFORE scheduling, effect intent BEFORE provider invocation or notification, and outcome BEFORE resumption. Journaling an entire runDurable call as one replayable operation is forbidden. The durable path deterministically reconstructs a segment from its immutable starting checkpoint and individually cached effect outcomes. A waiting result returns that starting checkpoint: do not replace it with an intermediate preview. The journal is required continuation data and must be retained with the checkpoint. Stable IDs include turn/segment and deterministic invocation identity. There is no live continuation or request-held promise while waiting. Runtimes serialize work per session, check cancellation before effects and before settlement, and fence ownership. Lost provider acknowledgement becomes uncertain; do not repeat it merely because a worker restarts. Tool calls are the exception: they are re-sent with their key, as above.

A terminal/paused result includes `result.state`. Save it. A new message uses a new turnId with prior completed state. Approval/response resumes paused state via a new checkpoint, same turnId, `segment + 1`, with `{kind:'approve',interactionId,approved}` or `{kind:'respond',interactionId,value}`. An action result simply reruns the SAME suspended checkpoint/segment after recording the outcome. `runDurable({yieldAfter: {steps, ms}})` lets a long turn end a segment at a step boundary with status `yielded` (Model Calls §10): the result state is mid-turn (status `active`, `turn` kept); save it, write a new checkpoint for the same turnId at `segment + 1` with input `{kind:'continue'}`, and schedule it. A yielded segment emits no `turn.*` event, and its effects are never read again. Paused plan records pending interactions/deferred calls; waiting on remote action is distinct from a human wait. Cancellation is host-owned and must fence both running and pending work. Runtime supplies canonical events; execution observations are not wire events and reconstruction must not republish duplicate history.

Host resolveEffect must bind the effect ID to the original request and reject drift. Intent/outcome, checkpoint settlement and canonical event/outbox writes must use runtime transactions. The Runtime journals individual effect boundaries, not the loop, in the Session Store under the advance's lease; Durable Session Execution (Restate) only runs one advance per session at a time and delivers wakes and timers, and journals no effects. Scheduling, storage, publication, delivery policy and reconciliation remain runtime-owned.

Agents used as tools: a manifest tool with an `agent` body (the child manifest inlined; name equals the child id, description equals the child description, input is the standard `{task}` schema, no outputSchema, no nested agent tools; the tree shares the session's one sandbox, whose spec the session keeps) is run by the engine inside the parent's `runDurable`. Its model and tool effects carry `agent: {id, path, delegationId}` (`delegationId` is the parent tool call's invocationId), keep the root `agentId` and `manifestHash`, and use identity `<delegationId>/<inner identity>`; tool context `idempotencyKey` is prefixed the same way. Hosts resolve child effects against the child manifest (`delegateManifest`) for pinned tool schemas and MCP routing, and include `agent` in `tool.completed` payloads; our engine gives each child its own skill tools and the session's sandbox tools. A `delegation` effect (identity `<delegationId>:started` or `<delegationId>:settled`, input `{task}` or `{status, outcome}`) must be recorded completed immediately with value null and publish `delegation.started` / `delegation.completed` exactly once; the journal makes replays silent. `DurableSessionTool.agentId` attaches discovered MCP tools to a child; MCP snapshot records and diagnostics carry `agentId`. Children share the session sandbox. `GET /v1/sessions/:id/items?agent=` filters history by `payload.agent.delegationId` or `payload.agent.path`. Existing checkpoints are unaffected; engine version stays `hosted-2`. A tool whose `agent` body is a flow agent (workflow manifest v3) is not run in-process: the engine issues one `agent` effect (identity `<delegationId>:flow`, input `{agentId, input: task, path}`, context `{role: "delegate", delegationId}`, `agent` ref set) between the `delegation` start and settle points. The host starts a linked flow session from the pinned parent manifest's inlined flow (session id `derive(parentSessionId, path, "delegate", delegationId)`), sends the task as its message, and completes the effect with the flow's output, or `{kind: "failed", code, message}`, when its turn ends. Cancelling the parent cascades to linked sessions.

**Workflows (flow engine).** Definitions with `kind: "workflow"` (workflow manifest v3) run through `createFlowCheckpoint` / `runFlowDurable` from `/run` (same `DurableResult` shape as `runDurable`) on engine `flow-3`; checkpoints pin it, and v1/v2 manifests are refused. The turn loop in `runtime/harness/src/loop/` is unchanged. A flow runs no developer code: its effects are `agent` (a leaf agent's turn) and `tool` (a workflow tool node). Each carries `path` (the leaf path: the leaf's id, `[i]` per Map item, nested flow agent ids in front), `key` (the path without Map indices) and `iterations` (enclosing Loop vector as a dotted string, or `"-"` outside Loops). Effect ids are `${turnId}:${segment}:flow:${path}:${kind}:${iterations}`. The first stage gets the flow's input and each later stage the previous output; a Switch reads it (a string, or its `route` field), a Map runs over it (an array, or its `items`), and a Loop asks a verifier (an agent, or an HTTP verifier) for a verdict (`{ pass, feedback? }`) and retries the body with the feedback, up to `max`. `agent` effect input is `{ agentId, input, path, flow?, flowInput? }`: `flow` names the nested flow agents, outermost first; `flowInput` is the flow agent's input, sent when the stage's input differs, and the host puts it in the linked message as the original request before the stage's input. Effect `context` carries `loopPath` and `n` for a Loop's turns, and `role: "verify-agent"` for its verifier, which gets a fresh session per attempt and whose verdict the host records as `loop.verified`. The host resolves the leaf from the workflow manifest's embedded `agents` (`embeddedAgent`) and gives the linked session the leaf's manifest and its hash, only through the public session contract (create linked session, message with derived idempotency key, settle on linked `turn.completed` / failed / cancelled). A `tool` effect carries `path` + `key` instead of `toolName`. A code tool node (no `http`) runs only in the local engine: the Runtime refuses a flow with one at save and fails such an effect with `tool.unavailable`. The `tool` effects of an HTTP stage (a tool node with `http`, input checked against its schema first) and of an HTTP verifier (`loop.verify: { http }`, input `{ input, output, iteration }`, `context.role: "verify-http"`, at the verify position's key) are requests the host makes through its Tool Gate as for an agent's HTTP tool, the effect id as `Idempotency-Key`, the HTTP outcome (`{ kind: "completed", output }` or `{ kind: "failed", code, message }`) as the value, and an HTTP verifier's verdict recorded as `loop.verified`; a Loop body that starts with an HTTP stage is retried with the Loop's input. A lost HTTP stage is sent again with the same key, as an agent's HTTP tool call is (R5). Parallelism comes from pending effects returned together; the Runtime caps concurrency with `RuntimeOptions.flow` / env (`maxConcurrency`, `maxMapItems`, `maxLoopIterations`).

**Turn manifests.** A `message` command may include optional `manifest`. Any app may use it (not only Loops). When present, the Runtime parses it with `AgentManifestSchema`, requires it to be a **variant** of the session's pinned manifest (id, `outputSchema` and skills fixed, plugin labels included; tools and delegates may only be removed; MCP servers may only be tightened; it has no `runtime` field), hashes and stores it by hash for that turn only (it does not latch — a later message without `manifest` uses the pin), and rebases `state.manifestHash` at turn start when the prior state hash and the turn hash are both the pin or validated variants of it. Invalid variants fail closed.

**Shared sandbox.** Definitions declare no sandbox; a session is opened with one (its Environment's), resolved against the Tenant's limits and pinned on the session (`Session.sandbox`). Since protocol 15 a session's manifest is its definition as registered, so its hash is the definition's: `turn.start` carries the spec as `routing.sandbox.spec` and the facts as `environment` (`{id, kind, sandbox?: {workspace}}`), and the harness writes the sandbox's instructions and defines the six sandbox tools, and `load_skill` and `read_skill_resource` with the skill catalog when the agent has skills (`engineToolsFor` in `@nylorun/harness`); a definition or a turn variant that sets `runtime` is refused; a workflow session's sandbox is stored beside its manifest the same way. A tree has one sandbox, keyed by the owning session id. `sandbox: { session }` attaches another session's sandbox (same `ownerUserId`, same Tenant); a session whose definition declares none inherits the owner's spec and tools. Linked agent sessions created for agent nodes attach with `sandbox: { session: workflowSessionId }` and inherit the same way. Application principals call `POST /v1/sessions/:id/sandbox/:tool` (`bash` | `read` | `write` | `edit` | `grep` | `glob`); refused while that session has an active agent turn. `session.sandbox` on the application client mirrors the session endpoint. Registration refuses a definition that declares a sandbox; definitions stored before Sandboxes v3 keep theirs.

## Harness API 4

The Runtime runs every segment through the Harness API (blueprint D37–D42): core keeps scheduling, the record, settle and takeover; a harness runs the engine. Three version numbers apply: the transport (path `/nylorun/harness/v1`, header `Nylorun-Harness-Api: 1`), the messages (`HARNESS_API_VERSION = 4`; core refuses a `hello` naming another `api`; 4 added the artifact seam, `artifact.read` and `artifact.write`, over which a harness reads and writes its run's session's artifacts, the error code `not_found`, `turn.start.model`, `turn.start.environment` and `turn.start.mcp` (the session's MCP discovery as raw facts), and each tool effect's `target` (an MCP or HTTP tool's identity), and removed `hello.features.tools`, `turn.start.sessionTools`, `routing.mcpSnapshot` and the `platform` target; 3 renamed `hello.capabilities` to `features` and dropped `capabilityId` from effect intents, MCP server refs, HTTP call bodies and MCP records) and the Runtime protocol, which only the Runtime and Management APIs carry. The whole contract is `@nylorun/core/harness-api` (R4.5): frames and messages, the transport and the pod join (`HostJoinRequestSchema`, `HostJoinAnswerSchema`), the Model and Tool Gate bodies (`ModelCallBodySchema`, `ToolCallBodySchema`, `HttpCallBodySchema`, MCP bodies, `GATE_ERROR_CODES`), the MCP snapshot (`McpSnapshotSchema`), transcript entries (`TranscriptEntrySchema`) and the effect id rule (`effectIdOf`: `<turnId>:<segment>:<kind>:<identity>`; a run gets back only its segment's outcomes), the request hash, transcript edits and the RPC channel; the Runtime validates with the same schemas, and the build writes them as one JSON Schema document (`@nylorun/core/harness-api/schema.json`). `TurnStart.trace` (optional W3C `traceparent`) is the turn's trace context when the Runtime traces. With the Tenant's fixture model on (`TurnStart.options.fixtureModel`, informational), the Model Gate answers model calls itself, metered like any model (provider `fixture`, cost 0), so a harness calls the gate as usual. Harness ids (R4.1): `hello.name` is the harness's id (ours says `nylorun`; `@nylorun/harness` is refused); a session pins its Environment's harness, else `nylorun`, and only a connection of that id takes its runs; a credential binds its id (the harness token is ours, a custom harness has its own from `nylorun-operate harness token put <id>`, a pod's host is its Environment's harness). A harness's state is its own (R4.2): core stores it unread; a custom harness's is at most 256 KiB, it cannot pause for approvals, and a tool it runs itself is a `harness` effect, journaled like ours. Events carry who wrote them (R4.9): `harness` with its id, `runId` and evidence `claimed` for what a harness reported. v2 removed held runs, `TurnStart.options.holdMs` and `effect.resolved`, with track R2; the harness client is `@nylorun/harness/api` (`createHarness({channel, executors, features?, mcpTools?, toolResults?})`: `mcpTools` how our engine defers MCP tools and `tool_search`'s limits, `toolResults` how it shapes tool results, each partial over its defaults). A Tenant runs one harness in its own process over a memory channel, or (F6.2, `NYLORUN_HARNESS=remote`) harnesses connect to core's Harness API listener over WebSocket (`/nylorun/harness/v1`, the harness credential): `--service harness` runs one with its own MCP pool and sandboxes and no store, and serves the Tenant's workspaces (`workspace.*`). Durable checkpoint 1 is unchanged.

Frames: `{t:"req",id,m,p}`, `{t:"res",id,ok,r|e:{code,message}}`, `{t:"msg",m,p}`, `{t:"abort",id}`, `{t:"ping"}`. Error codes: `run_not_held`, `turn_cancelled`, `ownership_lost`, `effect_drift`, `invalid`, `unavailable`, `internal`; the message is today's (`Turn cancelled`, `Effect identity request drift`, …).

- **Work.** `hello` → `{api, sandbox:{backend}, renewEveryMs}`. A harness keeps one `lease` waiting; an advance that took a session's lease offers its segment, and the answer is `{run: {runId, sessionId, turnId, epoch, token?, tokenExpiresAt?}, input: TurnStart}`. A run is bound to the connection that leased it. `lease.renew` every `renewEveryMs` renews the session's ownership lease (`{ok:false}`: lost, abort with `ownership.lost`); `lease.release{reason}` gives the run back (`shutdown`, `ownership.lost`; a lost connection counts as `connection.lost`).
- **Input.** `TurnStart` (`type` `turn.start`, or `approval.answer` for approve/respond): `engine` (`agent` | `flow`), the turn's `manifest`, the segment's `checkpoint` with an empty transcript, `mcp` (the session's MCP facts once discovered: each server's tools, raw, with `enabled` and a `deferred` hint; `session.mcp` records a snapshot and answers them), the segment's completed `outcomes` (`{effectId, requestHash, outcome}`), `transcript.cursor`, `options` (`yieldAfter`, `flowLimits`, `fixtureModel`) and `routing` (root manifest, plugin roots, sandbox owner). Core aborts a run with `cancel{runId, reason, message}`, `reason` one of `cancel`, `shutdown`, `deadline`, `ownership.lost`.
- **Record.** `requestHash = sha256(canonical(requestIdentity(effect)))` (canonical JSON: keys by code unit, `undefined` dropped; a delegation's identity leaves out `context`). An effect in `outcomes` with the same hash resolves in the harness; another hash is drift. Any other effect is an `effect.intent{effect, requestHash}`: a model intent carries no `input`, so a prompt never crosses twice. Core journals the row with `requestHash` (a model row without `input`) and answers `completed`, `pending`, `uncertain`, or `execute` (`rejoin` for a call its gate recovers, P1.2/F4.1). The harness runs model, MCP, HTTP and sandbox calls through the executors it is given (a model call reaches its provider through the Runtime's Model Gate, never from the harness) and reports `effect.outcome{value}` or `{error}` (uncertain for a model call; a tool call's error fails it to the model as `tool.interrupted`; a value past `limits.recordEntryBytes` is `limit_exceeded`, since the harness shapes tool results, not core); after a `shutdown` a recoverable call reports nothing and stays `invoking`. An intent for a tool row still `invoking` is a re-send (R5): core counts it and answers `execute` for an MCP or HTTP call under 3 sends, else the call's `tool.interrupted` outcome. A harness whose gate hop lost a call's answer asks again with the same intent. The Tool Gate runs a run's tool call only when its `Idempotency-Key` names an `invoking` row of the run's turn for the same tool and input, an MCP call's row targeting the same agent, server and raw tool name (`400 key_required`, `409 effect_not_journaled`). Core applies the Tenant's tool policy to an MCP or HTTP tool intent (R5 step 2), by the target's identity, never the model's name: one it refuses is answered `completed` with a `tool.denied` failure, and one it holds for a person is answered `pending` (the segment ends waiting; the turn pauses with an `approval` interaction whose id is the effect id, and the call is `execute`d once approved). Core runs flow work, linked sessions and delegation journaling, no tool of its own, and fails a tool that would run the developer's code (`tool.unavailable`), an MCP tool the session did not discover (`tool.unknown`) and one the turn disables (`tool.disabled`). Rows written before carry their full request and are hashed on read.
- **Transcript.** The cursor is the record seq of the last `transcript.updated`, `turn.cancelled` or `turn.failed`. A harness resumes from its cached transcript at that cursor, else reads it once (`transcript.read`). Outputs carry the agent's state without its transcript plus the `TranscriptUpdate[]` from the transcript the segment started with; core records them and answers with the new cursor.
- **Output.** `turn.completed`, `turn.paused`, `turn.waiting{status, effectIds}`, `turn.failed{status, error}` or `{thrown}`, and `checkpoint` for a yielded segment; answered `{cursor?}` once core settled it, idempotent per run and type. Core settles them exactly as the engine's own results, classifying aborts from its own signal.

A Runtime below F6.1 compares journal rows by their full request: downgrading one with a turn in flight can fail that turn with drift.

**Build your own harness.** A harness is any program that speaks this contract; it does not need `@nylorun/harness`. [`examples/harness-minimal`](../../examples/harness-minimal/) is one, written only against `@nylorun/core/harness-api`: it runs beside the Runtime with its own token (`nylorun-operate harness token put <id>`) and takes the sessions of Environments whose `harness` is its id, or runs as a pod Environment's `image`. `runtime/server/test/harness-api/conformance.test.ts` runs it against ours and the example.

## Definitions, validation, compatibility

`/define` is execution-free and browser-bundleable; Agent has no `.run()`. Explicit local execution uses `/run` run + bindingFromAgent(agent.build()). `/contracts` never imports checkpoint internals. Tools are supported remotely. JSON schemas are reconstructed through Zod's JSON Schema importer; unsupported schemas fail closed. The original manifest document must survive reconstruction. Runtime is the only hasher: it hashes the accepted manifest and pins that digest on the session. Agents do not hash. Model configuration is host-owned. The Runtime refuses a definition whose tools would run the developer's code. It checks an HTTP tool's answer against the tool's output schema and records a mismatch as the failed outcome `tool.invalid-output`.

No session migration, arbitrary checkpoint migration, broad model-support, or conformance claims follow from compiling this interface. Studio and conformance tooling remain outside production harness.
